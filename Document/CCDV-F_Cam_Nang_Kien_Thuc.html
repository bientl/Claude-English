Workflow vs Agent

Trọng tâm

Workflow: code định sẵn đường đi và gọi LLM theo các bước cố định. Agent: LLM tự quyết các bước và cách dùng tool trong vòng lặp, dựa trên feedback từ môi trường.

  • Workflow: dự đoán được, nhất quán, dễ test; hợp với task rõ ràng, các bước biết trước.
  • Agent: hợp với bài toán open-ended, số bước không đoán trước, không hard-code được đường đi.
  • Cả hai đều là agentic systems; khác nhau ở chỗ ai điều phối: code hay model.
  • Tín hiệu đề: "luôn cùng các bước theo thứ tự" → workflow; "tùy từng case, tự quyết bằng chứng" → agent.
Bẫy thi

Đề hay mô tả quy trình cố định (luôn 3–4 bước theo thứ tự) nhưng cài đáp án mồi "autonomous agent" nghe hiện đại. Bước cố định → workflow/prompt chaining; chỉ chọn agent khi đường đi phụ thuộc dữ liệu từng case.

Xem ví dụ: Kho hàng: hai loại request, hai mức tự chủ

Phần lớn request là kiểm tra tồn kho, luôn chạy cùng một câu query, nên dùng workflow do code điều phối. Số ít là chênh lệch tồn kho, cần so barcode, phiếu giao hàng, tóm tắt camera, và các bước khác nhau mỗi case, nên chuyển sang agent tự lập kế hoạch.

else:                                    # discrepancy: bước thay đổi theo case

Start simple: độ phức tạp phải được chứng minh

Trọng tâm

Bắt đầu bằng giải pháp đơn giản nhất chạy được, thường là một LLM call tốt kèm retrieval và ví dụ. Chỉ thêm bước, workflow hay agent khi eval cho thấy thật sự cần.

  • Leo thang dần: single call → thêm retrieval/examples → workflow (chaining, routing...) → agent.
  • Agentic system đổi latency và chi phí lấy hiệu năng; phải có lợi ích đo được mới đáng.
  • Đo bằng eval trên dữ liệu thực tế trước và sau mỗi lần thêm độ phức tạp.

Prompt chaining & programmatic gate

Trọng tâm

Chia task thành chuỗi bước cố định, output của call trước là input của call sau. Có thể chèn gate (kiểm tra bằng code) giữa các bước để dừng hoặc sửa khi kết quả trung gian không đạt.

  • Dùng khi task chia được thành subtask cố định, rõ ràng: viết → dịch, outline → draft → edit.
  • Đổi latency lấy độ chính xác: mỗi call chỉ làm một việc đơn giản hơn.
  • Gate = check programmatic (độ dài, schema, regex) trước khi đi tiếp; fail thì retry hoặc dừng chuỗi.
  • Dễ debug: biết chính xác bước nào sai và chỉ sửa prompt của bước đó.
Bẫy thi

Gate là kiểm tra bằng code, không phải "hỏi model xem ổn chưa" hay để agent tự quyết. Thấy "các bước cố định theo thứ tự + kiểm tra ở giữa" → prompt chaining with programmatic gate.

Xem ví dụ: Viết copy → kiểm tra 100 từ → dịch

Bước 1 viết marketing copy. Gate bằng code kiểm tra dưới 100 từ; nếu vượt thì yêu cầu rút gọn, vẫn fail thì dừng chuỗi. Chỉ khi qua gate mới sang bước 2 dịch sang tiếng Việt.

copy = call("Viết marketing copy cho sản phẩm X, dưới 100 từ.")

if len(copy.split()) > 100:                     # programmatic gate
    copy = call(f"Rút gọn dưới 100 từ:\n<copy>{copy}</copy>")
    if len(copy.split()) > 100:
        raise ValueError("Gate fail: dừng chuỗi")

vi = call(f"Dịch sang tiếng Việt:\n<copy>{copy}</copy>")

Routing

Trọng tâm

Bước đầu phân loại input (bằng LLM hoặc classifier), rồi chuyển tới prompt, tool set hoặc model chuyên biệt phù hợp với loại đó.

  • Hợp khi các loại input khác biệt rõ và xử lý riêng sẽ tốt hơn: refund / kỹ thuật / billing.
  • Tách mối quan tâm: tối ưu prompt cho loại này không làm hỏng loại khác.
  • Route theo độ khó để tiết kiệm: câu dễ → model nhỏ (Haiku), câu khó → model mạnh hơn.
  • Bước classify phải đủ chính xác; đo riêng nó bằng eval và có nhánh mặc định an toàn.
Bẫy thi

Phân biệt với orchestrator-workers: routing chọn MỘT nhánh cho cả input; orchestrator chia input thành NHIỀU subtask động. "Câu đơn giản → model nhỏ, phức tạp → model lớn, dựa trên bước phân loại" là routing.

Xem ví dụ: Inbox hỗ trợ: phân loại rồi chuyển nhánh

Model nhỏ phân loại email thành refund, technical hoặc billing. Mỗi nhãn có system prompt, tool set và model riêng; nhãn lạ rơi về nhánh mặc định.

label = call(MODEL_SMALL,

ROUTES = {
    "refund":    (MODEL_SMALL, REFUND_PROMPT,  refund_tools),

    "billing":   (MODEL_SMALL, BILLING_PROMPT, billing_tools),
}
model, system, tools = ROUTES.get(label, ROUTES["technical"])
answer = call(model, msg, system=system, tools=tools)

Parallelization: sectioning vs voting

Trọng tâm

Chạy nhiều LLM call cùng lúc rồi gộp kết quả bằng code. Hai biến thể: sectioning (chia thành các phần độc lập) và voting (chạy cùng một việc nhiều lần để lấy đồng thuận).

  • Sectioning: mỗi call lo một khía cạnh khác nhau (security / performance / style) → nhanh hơn, tập trung hơn.
  • Voting: cùng một câu hỏi, nhiều prompt hoặc nhiều lần chạy; chỉ flag khi đủ số phiếu → tin cậy hơn.
  • Guardrail kiểu sectioning: một call trả lời user, một call song song screen nội dung không phù hợp.
  • Các phần được xác định trước trong code, không do LLM lập kế hoạch.
Bẫy thi

Sectioning = các phần KHÁC nhau; voting = CÙNG một việc lặp nhiều lần. Nếu subtask không biết trước mà do LLM lên kế hoạch → orchestrator-workers, không phải parallelization.

Xem ví dụ: Code review song song và kiểm duyệt bằng bỏ phiếu

review() chạy 3 call cùng lúc, mỗi call một khía cạnh cố định, rồi gộp kết quả (sectioning). is_unsafe() chạy cùng một kiểm tra với 3 prompt khác nhau và chỉ flag khi ít nhất 2 phiếu đồng ý (voting).

import asyncio
ASPECTS = ["security", "performance", "style"]      # cố định trong code

async def review(diff):                             # sectioning
    res = await asyncio.gather(*[
        acall(f"Chỉ review {a}:\n<diff>{diff}</diff>") for a in ASPECTS])
    return dict(zip(ASPECTS, res))

async def is_unsafe(text):                          # voting
    votes = await asyncio.gather(*[
        acall(p.format(text=text)) for p in SAFETY_PROMPTS])  # 3 prompt
    return sum(v.strip() == "UNSAFE" for v in votes) >= 2

Orchestrator-workers

Trọng tâm

Một LLM trung tâm phân tích task, tự chia thành subtask động, giao cho các worker LLM rồi tổng hợp kết quả. Dùng khi không biết trước cần bao nhiêu hay những subtask nào.

  • Khác parallelization: subtask do orchestrator quyết theo từng input, không cố định trong code.
  • Ví dụ điển hình: sửa code ở số file chưa biết trước; research nhiều nguồn tùy câu hỏi.
  • Worker làm việc trong context riêng, trả kết quả cô đọng; orchestrator lo synthesis.
  • Tối ưu chi phí: orchestrator dùng model mạnh, worker làm việc đơn giản dùng model nhỏ hơn.
Bẫy thi

Từ khóa "tùy câu hỏi", "số file chưa biết", "LLM trung tâm lập kế hoạch rồi tổng hợp" → orchestrator-workers. Nếu số phần biết trước (luôn 3 khía cạnh) → parallelization sectioning.

Xem ví dụ: Trợ lý research: số lượt tìm kiếm thay đổi theo câu hỏi

Orchestrator (model mạnh) lập danh sách subtask dưới dạng JSON, số lượng thay đổi theo câu hỏi. Mỗi worker (model nhỏ) thực hiện một subtask và trả tóm tắt ngắn. Orchestrator tổng hợp thành câu trả lời cuối.

plan = call(MODEL_LARGE,
    f"Chia câu hỏi thành các truy vấn tìm kiếm, trả JSON list:\n{question}")
subtasks = json.loads(plan)          # 2 hay 7 subtask là tùy câu hỏi

findings = [call(MODEL_SMALL, f"Thực hiện và tóm tắt ngắn: {t}")
            for t in subtasks]       # worker: context riêng, kết quả gọn

report = call(MODEL_LARGE,
    f"Tổng hợp thành câu trả lời có dẫn nguồn:\n<findings>{findings}</findings>")

Evaluator-optimizer

Trọng tâm

Một call tạo output, một call khác đánh giá theo tiêu chí rõ ràng và đưa feedback; lặp tạo → chấm → sửa cho đến khi đạt hoặc hết số vòng cho phép.

  • Hợp khi có tiêu chí đánh giá rõ và mỗi vòng sửa cải thiện đo được: dịch văn học, mô tả sản phẩm, code.
  • Dấu hiệu phù hợp: feedback cụ thể giúp bản nháp tốt lên rõ, và LLM tự đưa được feedback đó.
  • Luôn đặt số vòng tối đa để tránh lặp vô hạn và tốn chi phí.
  • Evaluator nên trả kết quả có cấu trúc (PASS/FAIL + góp ý) để code quyết định dừng.
Bẫy thi

Đừng nhầm với voting: voting chạy song song để lấy đồng thuận; evaluator-optimizer là vòng lặp tuần tự có feedback. "Critique rồi revise cho đến khi pass" → evaluator-optimizer.

Xem ví dụ: Dịch văn học có vòng phê bình

Call thứ nhất dịch. Call thứ hai chấm theo tiêu chí sắc thái, giọng văn, độ chính xác và trả PASS/FAIL kèm góp ý. Nếu FAIL, call thứ nhất sửa theo góp ý; tối đa 3 vòng.

draft = call(f"Dịch, giữ sắc thái văn học:\n<src>{src}</src>")
for _ in range(3):                                  # giới hạn số vòng
    review = call(
        "Chấm bản dịch theo: sắc thái, giọng văn, chính xác. "
        "Dòng đầu ghi PASS hoặc FAIL, sau đó góp ý cụ thể.\n"
        f"<src>{src}</src>\n<draft>{draft}</draft>")
    if review.startswith("PASS"):
        break
    draft = call(f"Sửa theo góp ý:\n<feedback>{review}</feedback>\n<draft>{draft}</draft>")

Agent loop: plan → act → observe

Trọng tâm

Vòng lặp: model lập kế hoạch, gọi tool, nhận kết quả rồi quyết bước tiếp. Kết quả thật từ môi trường (tool result, output chạy code) là ground truth giữ agent bám thực tế.

  • stop_reason: "tool_use" → chạy tool, gửi tool_result có tool_use_id khớp trong lượt user, rồi gọi API tiếp.
  • stop_reason: "end_turn" và không có tool call → Claude đã xong, thoát vòng lặp.
  • Xử lý thêm: max_tokens (bị cắt), pause_turn (server tool chưa xong, gửi lại để tiếp), refusal.
  • API stateless: mỗi vòng gửi lại toàn bộ messages, gồm cả các block tool_use và tool_result.
  • Luôn kèm stopping criteria: số vòng tối đa, retry limit, checkpoint con người.
Bẫy thi

Đáp án mồi: "agent dựa vào kiến thức sẵn có" hoặc "prompt dài hơn" để giữ agent grounded. Đúng là feedback môi trường ở mỗi bước. end_turn → dừng; tool_use → chạy tool rồi gọi lại, không dừng.

Xem ví dụ: Vòng lặp tool use tối thiểu với Messages API

Mỗi vòng: gọi API, nối nội dung assistant vào history. Nếu tool_use thì chạy tất cả tool được yêu cầu và gửi mọi tool_result trong MỘT lượt user. Nếu pause_turn thì gọi lại để model tiếp tục. Các stop_reason khác thì thoát.

messages = [{"role": "user", "content": task}]
for step in range(MAX_STEPS):                       # luôn có giới hạn
    resp = client.messages.create(model=MODEL, max_tokens=4096,
                                  tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason == "tool_use":
        results = [{"type": "tool_result", "tool_use_id": b.id,
                    "content": run_tool(b.name, b.input)}
                   for b in resp.content if b.type == "tool_use"]
        messages.append({"role": "user", "content": results})
    elif resp.stop_reason == "pause_turn":
        continue                      # server tool chưa xong: gửi lại
    else:                             # end_turn, max_tokens, refusal...
        break

Stopping criteria, giới hạn vòng lặp & checkpoint

Trọng tâm

Agent cần điều kiện dừng rõ ràng: task hoàn thành, số vòng tối đa, giới hạn retry/timeout/ngân sách, và checkpoint để con người can thiệp khi cần.

  • Luôn đặt max iterations; trong Claude Agent SDK là max_turns, thêm max_budget_usd để chặn chi phí.
  • Giới hạn retry cho cùng một tool call; kết quả lặp y hệt → đổi hướng hoặc báo lỗi, đừng gọi tiếp.
  • Human checkpoint trước hành động rủi ro hoặc khi agent bị kẹt.
  • Chạm giới hạn: dừng có kiểm soát, ghi log, trả trạng thái rõ (vd error_max_turns).
Bẫy thi

Trace gọi get_job(8431) lặp nhiều lần cùng kết quả, max_iterations và retry_limit unset → đáp án là stop criteria + iteration limit + retry handling; không phải thêm subagent, memory hay payload lớn hơn.

Code đếm số lần gọi cùng một tool với cùng input. Gọi lặp quá 2 lần thì dừng và chuyển người xử lý; vượt MAX_STEPS cũng chuyển người. Trong Agent SDK, max_turns và max_budget_usd làm việc tương tự.

MAX_STEPS, MAX_SAME_CALL = 15, 2
seen = collections.Counter()
for step in range(MAX_STEPS):
    resp = call_model(messages)
    if resp.stop_reason != "tool_use":

else:

Chi phí của agent: latency, token, lỗi cộng dồn

Trọng tâm

Agent đổi lấy sự linh hoạt bằng latency cao hơn, nhiều token hơn, và lỗi có thể cộng dồn qua nhiều bước. Chỉ đáng dùng khi lợi ích vượt các chi phí đó.

  • Latency: nhiều vòng gọi model và tool tuần tự thay vì một call.
  • Token: Anthropic ghi nhận agent dùng khoảng 4x token so với chat, hệ multi-agent khoảng 15x.
  • Compounding errors: sai ở bước đầu lan sang các bước sau; cần guardrail và test trong sandbox.
  • Giảm thiểu: đúng mức tự chủ, giới hạn vòng lặp, model nhỏ cho bước đơn giản, caching.
Bẫy thi

Câu chọn 2 về chi phí agent: chọn "latency và token cost cao hơn" và "lỗi cộng dồn qua các bước". Loại các đáp án như "agent luôn chính xác hơn" hay "agent rẻ hơn".

Deterministic hooks vs model discretion

Trọng tâm

Hook là code chạy chắc chắn tại một điểm xác định trong vòng đời agent (trước/sau tool, khi kết thúc). Dùng cho việc bắt buộc phải xảy ra hoặc phải bị chặn, thay vì trông vào model tự nhớ.

  • Pre-action (PreToolUse): kiểm tra, chặn hoặc chuyển duyệt trước side effect, vd refund trên $100.

Đáp án mồi: "nhắc mạnh hơn trong prompt", "lưu vào memory", "để agent tự quyết". Đề có "must always" tại một điểm cụ thể, hoặc ngưỡng cần duyệt cứng → deterministic hook.

Hybrid design & right-sizing autonomy

Trọng tâm

Code deterministic lo các control bắt buộc (checklist, ngưỡng duyệt, lưu trữ, phân quyền); agent lo phần cần phán đoán. Mỗi phần chỉ được tự chủ vừa đủ với độ bất định của nó.

Hai đáp án cực đoan đều sai: "agent quyết tất cả" (kể cả control bắt buộc) và "fixed workflow cho tất cả, bỏ Claude". Chọn phương án chia: deterministic cho control, agent cho judgment.

Long-running agent: durable state & idempotency

Mở rộng

Agent chạy dài, có thể tạm dừng và được worker khác tiếp tục, cần lưu state ở nơi dùng chung bền vững và dùng idempotency key để retry không tạo side effect trùng.

  • State (bước đã xong, giấy tờ đang chờ, trạng thái duyệt) lưu trong DB dùng chung, không trong RAM một worker.
  • Mỗi action có side effect dùng idempotency key ổn định, vd create_account:task_123; retry dùng lại đúng key.
  • Không restart từ đầu với operation ID mới: hệ thống coi là action mới → tạo trùng.
  • Resume từ checkpoint gần nhất thay vì chạy lại toàn bộ task.
Bẫy thi

"Tạo operation ID mới khi retry" nghe sạch sẽ nhưng gây trùng; "giữ state trong worker đầu và route về đó" sẽ mất khi worker chết. Chọn shared durable state + idempotency key.

Xem ví dụ: Worker timeout sau khi đã tạo tài khoản

def create_account_step(task_id, customer):
    key = f"create_account:{task_id}"          # ổn định qua mọi lần retry
    done = db.get_action(key)
    if done:
        return done.result                     # đã ghi nhận: bỏ qua
    result = accounts_api.create(customer, idempotency_key=key)
    db.save_action(key, result)                # DB dùng chung cho mọi worker
    db.update_task(task_id, step="account_created")
    return result

asyncio.run(main())

stop_reason & cách xử lý

Trọng tâm

stop_reason cho biết vì sao Claude dừng sinh output. App phải đọc trường này để quyết định bước tiếp: trả kết quả, chạy tool, tăng max_tokens hay xử lý từ chối.

HTTP errors & lỗi nào nên retry

Trọng tâm

Lỗi API trả HTTP status kèm JSON error.type. Lỗi 4xx thường do request (sửa rồi gửi lại), còn 429, 500, 529 là lỗi tạm thời, nên retry với backoff.

  • Không retry (sửa request/config): 400 invalid_request_error, 401 authentication_error, 402 billing_error, 403 permission_error, 404 not_found_error, 413 request_too_large.
  • Retry với backoff: 429 rate_limit_error, 500 api_error, 529 overloaded_error; 504 timeout_error nên chuyển sang streaming.
  • 401 = key sai/thiếu; 403 = key hợp lệ nhưng không có quyền với tài nguyên.
  • 404 thường do sai model ID hoặc model đã ngừng; 413 khi vượt 32 MB (Messages).
  • Luôn log header request-id để debug và gửi Anthropic support.
Bẫy thi

Bẫy: retry 400/401 với backoff (vô ích, lỗi lặp lại) hoặc nhầm 401 với 403. 529 là API quá tải chung, khác 429 là bạn vượt giới hạn của mình. Cần hỗ trợ: đưa request-id, không phải API key.

Xem ví dụ: Phân loại lỗi trong code

Exponential backoff + jitter + retry-after

Trọng tâm

Khi gặp lỗi tạm thời, chờ khoảng tăng dần theo cấp số nhân (1s, 2s, 4s...) cộng độ ngẫu nhiên (jitter) trước khi retry, có giới hạn số lần. Nếu có header retry-after thì chờ ít nhất bấy nhiêu giây.

  • Jitter tránh "thundering herd": nhiều client không cùng retry một thời điểm.
  • retry-after là thời gian chờ tối thiểu; retry sớm hơn sẽ thất bại.
  • Chỉ retry lỗi tạm thời (429, 5xx, 529, lỗi kết nối); đặt trần số lần và thời gian chờ.
  • SDK chính thức tự retry lỗi kết nối, 429, 5xx: mặc định 2 lần, có backoff, tôn trọng retry-after.
  • Đổi số lần bằng max_retries (client hoặc per-request).
Bẫy thi

Bẫy: "retry ngay lập tức liên tục" hoặc "retry vô hạn". Đúng: chờ ≥ retry-after, rồi backoff có jitter và giới hạn số lần. Câu hỏi về SDK: mặc định tự retry có giới hạn, cấu hình được.

Xem ví dụ: Retry thủ công có jitter

Delay = min(trần, base × 2^lần) với full jitter, nhưng không ít hơn retry-after. Với SDK, thường chỉ cần chỉnh max_retries.

import random, time

def call_with_retry(fn, max_attempts=5, base=1.0, cap=30.0):
    for attempt in range(max_attempts):
        try:
            return fn()
        except anthropic.APIStatusError as e:
            if e.status_code not in (429, 500, 529) or attempt == max_attempts - 1:
                raise
            delay = random.uniform(0, min(cap, base * 2 ** attempt))
            ra = e.response.headers.get("retry-after")
            time.sleep(max(delay, float(ra)) if ra else delay)

client = anthropic.Anthropic(max_retries=4)   # hoặc để SDK tự lo

Rate limits: RPM, ITPM, OTPM

Trọng tâm

Giới hạn tốc độ tính theo từng model class ở 3 chiều: request/phút (RPM), input token/phút (ITPM), output token/phút (OTPM). Vượt bất kỳ chiều nào đều trả 429 rate_limit_error.

  • Ít request nhưng prompt rất lớn vẫn bị 429 do vượt ITPM.
  • Thuật toán token bucket: dung lượng hồi liên tục, không reset theo phút cố định.
  • Với đa số model, cache_read_input_tokens không tính vào ITPM, nên prompt caching tăng throughput.
  • Tăng traffic đột ngột có thể bị 429 (acceleration limit): tăng dần, giữ đều.
  • Header anthropic-ratelimit-* cho biết limit/remaining/reset; giới hạn theo usage tier của organization.
Bẫy thi

Bẫy: nghĩ rate limit chỉ đếm số request. Đề hay hỏi "ít request vẫn 429" → đáp án: giới hạn token/phút. Spend limit đạt trần cũng trả 429 nhưng không có retry-after, retry vô ích.

Mở rộng

Trong framework bất đồng bộ (FastAPI, aiohttp), dùng client async của SDK (AsyncAnthropic) để không chặn event loop. SDK còn cho cấu hình timeout và max_retries ở mức client hoặc từng request.

Bẫy thi

Claude Code hooks

Trọng tâm

Hook là lệnh shell (hoặc HTTP, prompt...) do Claude Code tự chạy ở các điểm cố định trong vòng đời như trước/sau khi gọi tool. Hook là control deterministic, khác với hướng dẫn mềm trong prompt hay CLAUDE.md.

  • Sự kiện chính: PreToolUse, PostToolUse, UserPromptSubmit, Stop, SubagentStop, SessionStart, PreCompact, Notification...
  • Exit code: 0 = thành công; 2 = chặn (stderr gửi cho Claude làm lý do); mã khác = lỗi không chặn, action vẫn chạy.
  • PreToolUse exit 2 chặn tool call; PostToolUse không chặn được vì tool đã chạy; Stop exit 2 bắt Claude làm tiếp.
  • Cũng có thể chặn bằng JSON: hookSpecificOutput.permissionDecision = deny (hoặc allow, ask).
  • Cấu hình trong .claude/settings.json dưới hooks, có matcher theo tên tool; xem bằng /hooks.
Bẫy thi

Hook in "blocked" rồi exit 0 thì lệnh VẪN chạy; phải exit 2 hoặc trả deny, và test bằng side effect thật (file còn nguyên). Việc "luôn luôn phải xảy ra" sau khi agent xong → hook (Stop/post-run), không dựa vào system prompt.

Xem ví dụ: Chặn lệnh đụng tới secrets/

Hook nhận JSON qua stdin (có tool_name, tool_input). Nếu lệnh Bash chứa secrets/, script in lý do ra stderr và exit 2, tool call bị chặn trước khi chạy. Kiểm thử bằng cách thử cat secrets/key.pem rồi xác nhận file không bị đọc/sửa.

// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{ "type": "command",
        "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-secrets.sh" }]
    }]
  }
}

# block-secrets.sh
cmd=$(jq -r '.tool_input.command')
if echo "$cmd" | grep -q 'secrets/'; then
  echo "Blocked: secrets/ is off-limits" >&2
  exit 2
fi
exit 0

Headless mode (-p) & CI

Trọng tâm

Headless (non-interactive) mode chạy Claude Code bằng claude -p "prompt": chạy một lượt rồi thoát, không cần terminal tương tác, phù hợp CI, script và pre-commit.

  • -p/--print: non-interactive; đọc được stdin, ví dụ cat error.log | claude -p "explain".
  • --output-format text|json|stream-json; json trả result, session_id, total_cost_usd...; thêm --json-schema để có structured_output.
  • --allowedTools "Read,Grep,Bash(git diff *)" cho phép đúng tool cần; --permission-mode dontAsk từ chối mọi thứ còn lại.
  • --continue/--resume <session_id> để nối tiếp; --bare bỏ qua hooks, CLAUDE.md, MCP tự phát hiện, khuyến nghị cho CI.
  • Tránh --dangerously-skip-permissions trong CI có quyền ghi thật.
Bẫy thi

Success criteria trước tiên

Trọng tâm

Thiết kế eval set

Trọng tâm

Phương pháp chấm: code, LLM, human

Trọng tâm

Có ba cách chấm eval: code-based (so khớp chính xác, regex), LLM-based (model chấm theo rubric) và human. Chọn theo bản chất đầu ra: có cấu trúc hay tự do, khách quan hay chủ quan.

  • Tài liệu hiện hành: Haiku 5.5, Sonnet 5.5, Opus 5.5 ($4/$20 per MTok); tier cao nhất là Fable 5.1 ($10/$50).
  • Trong cùng một model, output_config.effort cũng đánh đổi trí tuệ với latency và chi phí; đôi khi chỉnh effort hiệu quả hơn đổi model.
Bẫy thi

Đề hay gài "model lớn luôn tốt hơn" hoặc "model nhỏ không làm được gì phức tạp". Chọn câu tổng quát: nhỏ = nhanh, rẻ; lớn = năng lực cao hơn. Còn chọn cụ thể cho một tác vụ thì phải đo bằng eval.

Choosing a model with evals

Trọng tâm

Chọn model bằng cách chạy các model ứng viên trên eval set đại diện cho workload thật, rồi so sánh chất lượng, latency và chi phí. Mỗi endpoint có thể dùng một model khác nhau.

  • Tài liệu gọi eval set là "bước quan trọng nhất": dùng prompt và dữ liệu thật, gồm cả edge case.
  • So sánh 3 trục: accuracy/chất lượng, latency (p50, p95) và chi phí mỗi request.
  • Efficiency-first: bắt đầu từ Haiku, chỉ nâng cấp khi eval chỉ ra lỗ hổng năng lực cụ thể.
  • Capability-first: bắt đầu từ model mạnh (Opus), tối ưu prompt, rồi giảm effort hoặc hạ model để tiết kiệm.
  • Yêu cầu khác nhau thì model khác nhau: endpoint cần dưới 1 giây khác endpoint cần độ chính xác cao.
Bẫy thi

Phương án sai thường là "chọn theo benchmark công khai", "một model mạnh nhất cho mọi endpoint" hoặc "model rẻ nhất cho tất cả". Đáp án đúng luôn có ý "test trên workload/eval set đại diện" rồi chọn theo kết quả.

Mixed models in multi-agent systems

Trọng tâm

Trong hệ multi-agent, dùng model mạnh cho orchestrator (lập kế hoạch, tổng hợp) và model nhỏ, rẻ cho worker làm việc đơn giản, lặp lại, để phần lớn token được tính theo giá rẻ.

  • Orchestrator cần suy luận tốt để chia việc, giao subtask và tổng hợp kết quả, nên dùng model mạnh.
  • Worker làm việc hẹp, rõ ràng (tìm file, trích xuất, tóm tắt) dùng model nhỏ như Haiku, nhanh và rẻ.
  • Routing cũng là mixed models: bước phân loại đẩy câu dễ sang model nhỏ, câu khó sang model mạnh.
  • Mẫu khác: executor rẻ làm phần lớn công việc, chỉ escalate quyết định khó cho advisor mạnh.
  • Vẫn đo bằng eval để chắc chất lượng kế hoạch và kết quả cuối không giảm.
Bẫy thi

Bẫy: "hạ model của orchestrator để tiết kiệm" (làm hỏng chất lượng kế hoạch) hoặc "dùng model lớn cho tất cả". Đáp án đúng: capable orchestrator + smaller workers.

Latency levers

Trọng tâm

Giảm latency, đặc biệt time to first token (TTFT), bằng model nhanh hơn, streaming, output ngắn hơn và prompt caching cho phần prefix lặp lại.

  • Streaming (stream: true, SSE) hiển thị chữ đầu tiên gần như ngay; không giảm tổng thời gian sinh.
  • Model nhỏ, nhanh (Haiku, Sonnet) giảm cả TTFT lẫn tổng thời gian; cũng có thể giảm effort.
  • Output ngắn hơn thì ít token phải sinh: yêu cầu trả lời ngắn gọn và đặt max_tokens hợp lý.
  • Prompt caching giảm thời gian xử lý prefix dài lặp lại (system prompt, tài liệu).
  • Batch API không dành cho realtime: kết quả có thể mất tới 24 giờ.
Bẫy thi

Bẫy: chọn Batch API, bật extended thinking hoặc model lớn nhất cho chat widget cần phản hồi tức thì. Với câu "chữ đầu tiên xuất hiện gần như ngay", đáp án là fast model tier + streaming.

Cost levers

Trọng tâm

Chi phí bằng số token nhân đơn giá. Đòn bẩy chính: rút ngắn output (đắt hơn input khoảng 5 lần), đặt max_tokens, dùng Batch API, prompt caching và chọn model/effort phù hợp.

  • Output token thường đắt gấp khoảng 5 lần input: yêu cầu trả lời ngắn gọn và đặt max_tokens hợp lý.
  • Message Batches API giảm khoảng 50% cho việc không cần realtime (job đêm, xử lý hàng loạt).
  • Prompt caching: cache read chỉ khoảng 0.1x giá input, hợp với instructions hoặc tài liệu dùng chung.
  • Batch và caching cộng dồn được; thêm model nhỏ hơn cho tác vụ dễ.

Prompt caching basics

Trọng tâm

Prompt caching lưu phần prefix lặp lại của prompt (đánh dấu bằng cache_control) để các request sau đọc lại thay vì xử lý từ đầu, giảm chi phí và latency.

  • Đặt breakpoint "cache_control": {"type": "ephemeral"} ở cuối phần tĩnh; nội dung thay đổi đặt sau nó.
  • TTL mặc định 5 phút, được làm mới miễn phí mỗi lần hit; tùy chọn "ttl": "1h".
  • Giá: write 1.25x (5 phút) hoặc 2x (1 giờ); read khoảng 0.1x giá input (Opus/Sonnet 5.5 chỉ 0.05x).
  • Automatic caching: đặt cache_control ở top-level request, hệ thống tự gắn breakpoint vào block cuối; vẫn tính phí write.
  • Khớp chính xác toàn bộ prefix; request song song chỉ hit cache sau khi response đầu tiên bắt đầu.
Bẫy thi

Bẫy: "cache tự động, miễn phí, không cần làm gì" hoặc "cache lưu cả output". Đúng: phải opt-in bằng cache_control; ghi cache đắt hơn input thường, đọc rẻ hơn nhiều; TTL mặc định 5 phút, làm mới khi dùng.

Cache prefix order & invalidation

Trọng tâm

Cache dựa trên prefix theo thứ tự tools → system → messages. Thay đổi ở một mức sẽ vô hiệu cache của mức đó và mọi mức phía sau.

  • Thứ tự prefix: tools → system → messages; breakpoint cache toàn bộ nội dung đứng trước nó.
  • Thêm hoặc sửa tool definition làm mất cache của cả tools, system và messages.
  • Đổi tool_choice hoặc thêm/bớt ảnh chỉ làm mất cache phần messages; tools và system vẫn giữ.
  • Nội dung động (timestamp, user ID, request ID) ở đầu prompt phá cache mọi request; đặt chúng sau breakpoint.
  • JSON key order không ổn định trong input của tool_use cũng làm hỏng cache.
Bẫy thi

Đề hay hỏi "thêm một tool mới thì cache system prompt ra sao?": bị vô hiệu vì tools đứng trước system. Và "cache read luôn bằng 0" khi có timestamp ở đầu: prefix khác nhau ở mỗi request nên không gì phía sau được đọc từ cache.

Caching in multi-turn chat & breakpoints

Trọng tâm

Trong hội thoại nhiều lượt, dời breakpoint cache_control tới cuối hội thoại ở mỗi lượt để các lượt trước được đọc từ cache. Mỗi request có tối đa 4 breakpoint.

  • Tối đa 4 breakpoint cache_control mỗi request; automatic caching chiếm 1 trong 4 slot.
  • Mỗi lượt: gắn breakpoint vào block cuối của message mới nhất; lượt sau đọc cache phần cũ, ghi thêm phần mới.
  • Automatic caching (cache_control ở top-level) tự dời breakpoint theo hội thoại, không cần quản lý thủ công.
  • Lookback tối đa 20 block mỗi breakpoint; hội thoại rất dài có thể cần thêm breakpoint trung gian.
  • Dùng nhiều breakpoint cho các phần đổi với tần suất khác nhau: tools, system, tài liệu, lịch sử chat.
Bẫy thi

Bẫy: "giữ breakpoint cố định ở lượt đầu" (phần mới không bao giờ được cache) hoặc "đặt breakpoint ở mọi message" (vượt giới hạn 4, lỗi 400). Đáp án đúng: moving breakpoint ở cuối hội thoại.

Xem ví dụ: Chatbot hỗ trợ nhiều lượt

Mỗi lượt, ứng dụng gỡ cache_control khỏi message cũ và gắn vào block cuối của user message mới, nên toàn bộ lịch sử trước đó được đọc từ cache. Cách đơn giản hơn trên tài liệu hiện hành: bật automatic caching ở top-level.

def add_turn(history, new_user_text):
    for m in history:                       # gỡ breakpoint cũ
        if isinstance(m["content"], list):
            for b in m["content"]:
                b.pop("cache_control", None)
    history.append({"role": "user", "content": [{
        "type": "text", "text": new_user_text,
        "cache_control": {"type": "ephemeral"}  # luôn ở cuối
    }]})
    return history

Verifying the cache

Trọng tâm

Kiểm tra cache qua usage: cache_creation_input_tokens > 0 là vừa ghi cache, cache_read_input_tokens > 0 là đã đọc từ cache. Prefix ngắn hơn ngưỡng tối thiểu sẽ không được cache.

  • cache_read_input_tokens > 0: request đã dùng cache (cache hit).
  • cache_creation_input_tokens > 0: request vừa ghi cache; input_tokens là phần sau breakpoint cuối, không cache.
  • Tổng input = cache_read_input_tokens + cache_creation_input_tokens + input_tokens.
  • Ngưỡng tối thiểu tùy model: 512 (Opus/Sonnet/Haiku 5.5), 1.024, 2.048 hoặc 4.096 token (Opus 4.5, Haiku 4.5).
  • Dưới ngưỡng: không báo lỗi, chỉ âm thầm không cache, cả hai trường cache đều bằng 0.
Bẫy thi

Bẫy: kiểm tra bằng latency hoặc một header nào đó. Đáp án: usage.cache_read_input_tokens > 0. System prompt 200 token có cache_control mà không bao giờ cache: prefix ngắn hơn ngưỡng tối thiểu (tài liệu cũ ghi 1.024/2.048; 200 vẫn dưới mọi ngưỡng).

Extended / adaptive thinking

Trọng tâm

Extended/adaptive thinking cho Claude suy luận nội bộ trước khi trả lời. Hữu ích cho tác vụ nhiều bước phức tạp; với câu hỏi đơn giản chỉ tốn thêm latency và output token.

Be clear & direct (kèm context và lý do)

Trọng tâm

Viết prompt rõ ràng, cụ thể như đang giao việc cho một đồng nghiệp mới: nêu mục tiêu, đối tượng, bối cảnh, tiêu chí kết quả tốt và giải thích VÌ SAO cần làm vậy.

  • Golden rule: đưa prompt cho đồng nghiệp ít context đọc thử; họ bối rối thì Claude cũng bối rối.
  • Nêu audience, mục đích, định dạng đầu ra và thế nào là 'kết quả tốt'.
  • Giải thích lý do sau chỉ dẫn giúp Claude tự khái quát sang trường hợp tương tự.
  • Muốn kết quả 'vượt mong đợi' thì phải yêu cầu rõ, đừng mong model tự đoán.
  • Chia yêu cầu thành các bước đánh số khi thứ tự hoặc độ đầy đủ quan trọng.
Bẫy thi

Đáp án sai thường là prompt ngắn mơ hồ ('Make this report better') hoặc chỉ viết HOA 'NEVER ...' không kèm lý do. Chọn phương án có context + lý do + tiêu chí thành công cụ thể.

Trọng tâm

System prompt & role prompting

Trọng tâm

System prompt (tham số system top-level) chứa phần bền vững áp dụng mọi lượt: vai trò, giọng điệu, quy tắc cố định, bối cảnh nghiệp vụ. Câu hỏi/tác vụ cụ thể đặt trong lượt user.

  • Đặt role trong system prompt; chỉ một câu như 'You are a senior tax analyst' cũng tạo khác biệt.
  • Role càng cụ thể (ngành, cấp bậc, người đọc) thì giọng điệu và chuyên môn càng sát.
  • System = ai, như thế nào, luật gì; messages = hỏi gì lúc này.
  • Không bao giờ đặt API key, mật khẩu hay secret trong system prompt.
  • Phần system ổn định là ứng viên tốt cho prompt caching; dữ liệu từng khách hàng đi theo conversation riêng.
Bẫy thi

Bẫy: đặt role trong tool description, metadata hay cuối user message; đưa secret vào system prompt; gộp nhiều khách hàng vào một conversation để 'viết instructions một lần'. Đúng là: role + quy tắc ở system, mỗi khách hàng một conversation riêng.

Chain of thought (CoT) & tách câu trả lời

Trọng tâm

Cho Claude suy luận từng bước trước khi trả lời để tăng độ chính xác ở bài toán nhiều bước. Khi không bật thinking, yêu cầu suy luận trong <thinking> và đặt kết quả trong <answer> để dễ trích xuất.

  • Mẫu kinh điển (đáp án đề thi): suy luận trong <thinking>, kết quả cuối trong <answer>, code chỉ lấy <answer>.
  • Output phải có phần suy luận viết ra; chỉ nói 'think step by step' mà không cho viết thì không có tác dụng.
  • CoT tăng output tokens và latency; dùng cho toán, phân tích, quyết định phức tạp, không cho câu tra cứu đơn giản.
  • Docs hiện hành: model mới (Opus 5.5, Sonnet 5.5) nên dùng thinking với effort thấp; yêu cầu viết <thinking> có thể bị từ chối.
  • Chỉ dẫn chung kiểu 'think thoroughly' thường tốt hơn kịch bản từng bước viết tay.
Bẫy thi

Đề hỏi 'không dùng thinking feature mà vẫn suy luận và dễ trích đáp án' thì chọn <thinking> + <answer>. Đừng chọn tăng temperature, giảm max_tokens hay yêu cầu 'chỉ trả lời'. Lưu ý thực tế: model mới ưu tiên adaptive thinking thay cho CoT thủ công.

Trọng tâm

  • Cho phép rõ ràng: 'Nếu tài liệu không đề cập, hãy nói bạn không biết'.
  • Trích quote nguyên văn (word-for-word) trước, rồi chỉ trả lời dựa trên các quote đó.
  • Bật citations trên document block để mỗi khẳng định gắn với cited_text cụ thể.
  • Giới hạn kiến thức: chỉ dùng tài liệu cung cấp, không dùng kiến thức chung.
  • Kỹ thuật thêm: tự kiểm tra lại từng khẳng định, so sánh nhiều lần chạy (best-of-N).
Bẫy thi

Trọng tâm

Tách một tác vụ lớn thành chuỗi prompt nhỏ, mỗi bước một API call riêng, output bước trước làm input bước sau. Mỗi bước dễ làm tốt hơn, dễ debug, log và kiểm tra hơn.

  • Mỗi bước có một mục tiêu rõ (research → outline → draft → edit).

  • Tài liệu hiện hành: thinking xử lý nhiều suy luận nội bộ; chaining vẫn hữu ích khi cần kiểm tra kết quả trung gian.

Trọng tâm

Context window là tổng số token model xử lý trong một request: mọi thứ gửi vào (system, messages, tool definitions, tool results, ảnh/PDF) cộng output được sinh ra, kể cả thinking.

  • Tính cả: system prompt, toàn bộ messages, tool_use/tool_result, định nghĩa tools, ảnh, PDF, output và thinking.
  • API stateless: mỗi request gửi lại toàn bộ lịch sử nên context tăng dần theo lượt.
  • Prompt cache vẫn chiếm context window; caching chỉ đổi giá, không đổi số token tính.
  • max_tokens chỉ giới hạn output, không mở rộng context. Input quá dài: lỗi 400 'prompt is too long'.
  • Claude 4.5+: chạm giới hạn khi sinh thì dừng với stop_reason model_context_window_exceeded. Ước lượng trước bằng count_tokens.
Bẫy thi

Bẫy: quên tool definitions và tool results cũng tốn token, hoặc nghĩ API tự nhớ các lượt trước. Khi đề hỏi cái gì được tính, chọn đáp án bao quát nhất. Tăng max_tokens không giải quyết context đầy.

Trọng tâm

Quản lý thông tin đưa vào context của agent chạy dài: chọn tập token nhỏ nhất mà giá trị cao nhất. Kỹ thuật chính: compaction, ghi chú/memory bên ngoài, subagent với context riêng.

  • Context là tài nguyên hữu hạn; quá dài gây 'context rot', chất lượng giảm trước cả khi chạm giới hạn.
  • Compaction: tóm tắt lịch sử cũ, bỏ dữ liệu thô đã dùng xong (kết quả search, tool output).

Least privilege for tools & credentials

Trọng tâm

Mỗi tool hoặc agent chỉ được cấp đúng quyền tối thiểu cần cho nhiệm vụ: tài khoản read-only, giới hạn bảng, thư mục hay API, credential có phạm vi hẹp và thời hạn ngắn.

  • Agent chỉ cần đọc dữ liệu thì dùng DB account read-only, chỉ trên các bảng cần thiết.
  • Giảm excessive agency (OWASP LLM06): ít tool, ít quyền, ít tự chủ hơn với hành động rủi ro.
  • Khi bị prompt injection, least privilege giới hạn thiệt hại: model không làm được điều tool không cho phép.
  • Credential theo phạm vi: mỗi khách hàng hoặc user một token ngắn hạn, không dùng admin token chung.
  • Trong Claude Code: allow rule hẹp như Bash(npm run test *) thay vì cho phép mọi lệnh.
Bẫy thi

Bẫy: dùng tài khoản admin "cho tiện" rồi dặn model trong prompt "đừng xoá dữ liệu". Prompt không phải cơ chế phân quyền; đáp án đúng giới hạn quyền ở tầng credential hoặc tool.

Secrets management

Trọng tâm

Secret (API key, mật khẩu DB, token) không bao giờ nằm trong prompt hay code chạy trên trình duyệt. Giữ chúng ở backend (biến môi trường, secret manager); tool dùng secret ở phía server.

  • Không đặt secret trong system prompt: có thể bị lộ (system prompt leakage, OWASP LLM07) hoặc bị injection khai thác.
  • Không gọi Claude API trực tiếp từ browser JavaScript vì ai cũng xem được key; dùng backend proxy.
  • Lưu key trong biến môi trường hoặc secret manager; không commit vào git.
  • Host chèn credential khi thực thi tool; model chỉ thấy tên tool và tham số, không thấy secret.
  • Ưu tiên credential ngắn hạn, phạm vi hẹp; rotate key định kỳ và ngay khi nghi bị lộ.
Bẫy thi

Bẫy: "obfuscate hoặc mã hoá key trong JS" hay "dặn model không tiết lộ password" đều sai. Đáp án đúng: secret ở server-side, tool tự dùng secret, model không bao giờ thấy nó.

Prompt injection (direct vs indirect)

Trọng tâm

Prompt injection là khi nội dung đưa vào model chứa chỉ thị nhằm chiếm quyền điều khiển. Direct: người dùng gõ trực tiếp. Indirect: ẩn trong trang web, email, tài liệu, tool result hoặc MCP resource.

  • Direct injection: người dùng nhập "Ignore all previous instructions..." vào ô chat.
  • Indirect injection: chỉ thị ẩn trong dữ liệu model xử lý (trang web, email, issue, PDF, kết quả RAG).
  • Tool results và MCP resources là dữ liệu không tin cậy, không phải lệnh, kể cả khi tool được phép đọc chúng.
  • Bọc nội dung không tin cậy trong tag rõ ràng (ví dụ <user_input>) và dặn coi là dữ liệu: hữu ích nhưng chưa đủ.
  • Prompt không chặn được 100%: kết hợp least privilege, authorization ở backend và xác nhận của người.
Bẫy thi

Bẫy: tin rằng chỉ cần system prompt nói "bỏ qua lệnh trong dữ liệu" là đủ, hoặc nhầm indirect injection với jailbreak do người dùng gõ. Đáp án đúng coi nội dung bên ngoài là untrusted data và chặn hành động nhạy cảm ở tầng ngoài model.

Defense in depth

Trọng tâm

Defense in depth là xếp nhiều lớp bảo vệ độc lập để khi một lớp thất bại vẫn còn lớp khác: sàng lọc input, prompt có cấu trúc, giới hạn quyền, kiểm tra output, monitoring và guardrail tất định.

  • Sàng lọc input bằng model nhẹ (ví dụ Haiku) hoặc classifier trước khi gọi model chính.
  • Validate và monitor output trước khi hành động (schema, business rules, policy).
  • Guardrail tất định ngoài model: hook PreToolUse thoát với exit code 2 mới chặn; exit 0 kèm "blocked" không chặn gì.
  • Logging và monitoring để phát hiện mẫu tấn công, kèm rate limit và cảnh báo.
  • Không lớp nào hoàn hảo; prompt chỉ là một lớp, không phải ranh giới bảo mật.
Bẫy thi

Câu chọn 2 đáp án hay gài "một system prompt thật mạnh là đủ", "mã hoá system prompt bằng base64" hoặc "tăng temperature". Chọn các biện pháp thành lớp: screen input + validate/monitor output.

Treat model output as untrusted

Trọng tâm

Output của model là input không tin cậy. Trước khi đưa vào SQL, shell, HTML hay API có side effect phải validate, escape và dùng parameterized queries (OWASP LLM05: Improper Output Handling).

  • Không nối chuỗi output vào câu SQL; dùng parameterized queries hoặc prepared statements.
  • Validate theo schema và allowlist (cột, bảng, trạng thái hợp lệ) trước khi thực thi.
  • Escape khi render HTML để tránh XSS; không eval() hay chạy shell trực tiếp từ output.
  • Structured outputs đảm bảo đúng format JSON, nhưng vẫn phải kiểm tra business rules và quyền.
  • Kiểm tra trước side effect (ghi DB, gửi email, thanh toán), không phải sau.
Bẫy thi

Bẫy: "Claude đáng tin nên chèn thẳng output" hoặc "chỉ cần dặn model đừng sinh SQL độc hại". Đáp án đúng: đối xử với output như input người dùng, tức validate + parameterized query.

Authorization enforced in the backend

Trọng tâm

Phân quyền phải được thực thi ở backend của tool dựa trên danh tính user đã xác thực, không dựa vào lời dặn trong prompt hay tham số do model tự điền.

Human-in-the-loop for high-impact actions

Trọng tâm

Human-in-the-loop: hành động không thể đảo ngược hoặc tác động lớn (hoàn tiền, xoá dữ liệu, gửi email ra ngoài, thanh toán) phải có người duyệt trước khi thực hiện.

  • Phân loại theo rủi ro: đọc và điều tra rủi ro thấp để agent tự chủ; hành động không đảo ngược cần duyệt.
  • Thực thi bằng cơ chế tất định (hook trước khi gọi tool, workflow approval), không dựa vào model tự giác.
  • Đặt ngưỡng rõ ràng, ví dụ hoàn tiền trên $100 phải chuyển cho người duyệt.
  • Agent chạy dài cần thêm stopping conditions (max iterations) và checkpoint cho người.
  • Cho người duyệt đủ ngữ cảnh: hành động, tham số, lý do.
Bẫy thi

Bẫy: "cho agent tự quyết, miễn prompt dặn cẩn thận" hoặc "duyệt mọi thứ kể cả đọc dữ liệu" (quá mức, mất lợi ích của agent). Đáp án đúng: human approval cho hành động irreversible/high-impact.

Xem ví dụ: Hook chặn hoàn tiền lớn

#!/usr/bin/env python3

Privacy: minimization, masking, log retention

Trọng tâm

Bảo vệ dữ liệu cá nhân: chỉ gửi và lưu dữ liệu thật sự cần (data minimization), che PII mà tác vụ không cần, và giới hạn ai đọc được log cùng thời gian lưu giữ.

  • Data minimization: bỏ trường không cần (số CCCD, số thẻ, địa chỉ) trước khi gửi cho model.
  • Mask hoặc pseudonymize PII trong prompt và log, ví dụ thay email bằng <EMAIL>; map ngược ở backend nếu cần.
  • Giới hạn quyền đọc log và đặt thời hạn lưu giữ (retention), tự xoá khi hết hạn.
  • Không đưa dữ liệu của khách hàng này vào ngữ cảnh của khách hàng khác.
  • Liên quan OWASP LLM02 Sensitive Information Disclosure: lộ dữ liệu qua output, log hoặc lưu trữ.
Bẫy thi

Bẫy: "lưu toàn bộ prompt và response vô thời hạn để debug" hoặc "dặn model đừng nhắc PII". Đáp án đúng: minimization + masking trước khi gửi và ghi log, cùng với kiểm soát truy cập và retention của log.

Tool definition (name, description, input_schema)

Trọng tâm

Tool use loop (tool_use → tool_result)

Trọng tâm

Khi Claude muốn gọi client tool, response có stop_reason: "tool_use" và block tool_use (id, name, input). Code của bạn chạy tool, gửi tool_result với tool_use_id khớp rồi gọi API lại.

  • Claude không tự chạy client tool: nó chỉ đề xuất lời gọi; ứng dụng validate input, thực thi và trả kết quả.
  • Gửi lại nguyên response.content làm assistant message, sau đó một user message chứa các block tool_result.
  • tool_result phải ngay sau message có tool_use; trong user message, tool_result đứng trước mọi text (sai → lỗi 400).
  • content của tool_result có thể là chuỗi hoặc block text, image, document, search_result.
  • Lặp đến khi stop_reason là end_turn, kèm giới hạn số vòng lặp do bạn đặt.
Bẫy thi

Đáp án sai hay gặp: "chờ Claude tự truy vấn", "đưa kết quả vào system prompt", "gửi kết quả ở conversation mới". Đúng: validate input → chạy tool → tool_result có tool_use_id khớp id → gọi API tiếp với đủ lịch sử.

Trọng tâm

Khi tool lỗi (exception, timeout, input sai), vẫn phải trả tool_result cho đúng tool_use_id, đặt is_error: true kèm thông báo cụ thể để Claude tự điều chỉnh.

Bẫy: "dừng cuộc hội thoại", "trả tool_result rỗng như thành công", "retry vô hạn trong code mà không báo Claude". Đúng: tool_result + is_error: true + thông điệp actionable.

Client tools vs server tools, pause_turn

Mở rộng

Client tool do code của bạn thực thi và trả tool_result. Server tool (web_search, web_fetch, code_execution, tool search) chạy trên hạ tầng Anthropic; kết quả nằm sẵn trong response, bạn không trả tool_result.

  • Server tool hiện thành block server_tool_use kèm block kết quả (ví dụ web_search_tool_result) trong cùng response.
  • pause_turn: vòng lặp server chạm giới hạn (mặc định 10 vòng); gửi lại nguyên response.content làm assistant message, giữ nguyên tools.
  • Gọi lẫn server và client tool: stop_reason là tool_use; chỉ trả tool_result cho client tool, không thêm text.
  • Server tool có thể tính phí theo lượt dùng ngoài token, ví dụ web search tính theo số lần tìm.
  • Tool có schema do Anthropic định nghĩa như bash, text_editor, computer vẫn là client tool: bạn tự thực thi.
Bẫy thi

Tool do code bạn implement (ví dụ check_stock) thì Claude không tự truy vấn, đừng chọn "chờ Claude". Với pause_turn, đừng thêm câu "continue" hay sửa block; chỉ gửi lại assistant content y nguyên.

Xem ví dụ: Xử lý pause_turn khi dùng web search

Câu hỏi nghiên cứu khiến Claude tìm web nhiều lần, chạm giới hạn vòng lặp server và trả pause_turn. Code gửi lại assistant content không đổi để Claude làm tiếp, đặt trần số lần tiếp tục.

for _ in range(5):  # trần số lần tiếp tục

                                  tools=tools, messages=messages)
    if resp.stop_reason != "pause_turn":
        break  # end_turn, tool_use (client tool), refusal...
    # Gửi lại nguyên văn, không thêm text, giữ nguyên tools
    messages = [{"role": "user", "content": question},
                {"role": "assistant", "content": resp.content}]

MCP architecture: host, client, server

Trọng tâm

MCP (Model Context Protocol) là chuẩn mở kết nối ứng dụng AI với tool và dữ liệu. Host (Claude Code, Claude Desktop, IDE) tạo một MCP client cho mỗi server; client và server trao đổi bằng JSON-RPC 2.0.

  • Một host chạy một hoặc nhiều client; mỗi client giữ kết nối 1:1 riêng với một server.
  • Hai lớp: data layer (JSON-RPC 2.0, primitives, notifications) và transport layer (stdio, Streamable HTTP, xác thực).
  • Lợi ích chính: build integration một lần thành MCP server, mọi client tương thích MCP đều dùng được.
  • Client khám phá qua tools/list, resources/list, prompts/list; thực thi bằng tools/call.
  • Spec mới (2026-07-28) chuyển sang stateless: mỗi request mang version và capabilities trong _meta, thêm server/discover.
Bẫy thi

Q163: chọn "host chạy một hoặc nhiều client, mỗi client kết nối 1:1 với một server"; loại "một client dùng chung cho mọi server". Q050: lợi ích là tái sử dụng (build once, use everywhere), không phải "nhanh hơn" hay "bỏ qua xác thực".

MCP primitives: tools, resources, prompts

Trọng tâm

MCP server cung cấp ba primitive phân theo ai điều khiển: tools (model-controlled, hàm thực thi), resources (application-controlled, dữ liệu ngữ cảnh có URI), prompts (user-controlled, template như slash command).

  • Tools: có inputSchema (JSON Schema), dùng tools/list và tools/call; cho hành động hoặc tính toán có input.
  • Resources: URI + MIME type (file:///docs/handbook.md), hỗ trợ template policy://handbook/{section}; đọc qua resources/read.
  • Prompts: template có tham số, người dùng chủ động chọn (prompts/list, prompts/get), thường hiện thành slash command.
  • Client feature: elicitation (server xin thêm input từ user); sampling và roots bị deprecated từ spec 2026-07-28.
  • Nội dung resource và tool result là dữ liệu không tin cậy, có thể chứa prompt injection; kiểm tra quyền ở backend.
Bẫy thi

Q079: sổ tay chính sách duyệt theo mục → resources; máy tính lương nhận input → tool. Q118: "model quyết định khi nào gọi" → tools. Đừng nhầm prompts (user-controlled) với system prompt; text trong resource không phải lệnh (Q093).

Xem ví dụ: MCP server cho phòng nhân sự

Sổ tay chính sách là dữ liệu đọc, ứng dụng cho người dùng duyệt từng mục → resource template. Máy tính lương thực nhận có input kiểu số → tool. Mẫu "xem xét đơn nghỉ phép" người dùng tự chọn → prompt.

MCP transports: stdio vs Streamable HTTP

Trọng tâm

MCP có hai transport chuẩn: stdio, nơi client spawn server thành subprocess cục bộ và trao đổi JSON-RPC qua stdin/stdout; và Streamable HTTP cho server từ xa, client gửi HTTP POST, server có thể stream bằng SSE.

  • stdio: không mở cổng mạng, độ trễ thấp, vòng đời gắn với client; thường chỉ phục vụ một client.
  • stdio: chỉ ghi message MCP ra stdout; log phải ghi ra stderr, nếu không sẽ làm hỏng luồng JSON-RPC.
  • Streamable HTTP: một endpoint HTTP, phục vụ nhiều client, xác thực bằng bearer token hoặc API key; khuyến nghị OAuth.
  • Transport HTTP+SSE cũ (spec 2024-11-05) đã deprecated, được thay bằng Streamable HTTP.
  • Claude Code: claude mcp add --transport http <name> <url> cho remote; claude mcp add <name> -- <command> cho stdio.
Bẫy thi

Q127: server chạy dạng subprocess cục bộ trên cùng máy → stdio. Server dùng chung qua mạng → Streamable HTTP. WebSocket hay gRPC không phải transport chuẩn của MCP.
